# Phase 1 protected recovery procedure and acceptance gates

15 November 2026. This documents the OWNER APPROVED disposable TEST implementation. Production remains DISABLED. These private APIs are not a production operator console; trusted packaged entry, real custody and device acceptance are separate gates. Phase 2/3 have not started.

1. Use patched Node 24.22.3 and an existing verified protected current admission. Preserve original databases, vaults, all migration bytes and every financial/audit record. Maintenance uses the existing sole authorization owner, a fresh existing Admin credential and the same machine-wide runtime lease. No reset, schema shortcut or automatic migration is permitted.
2. A protected backup produces an age ciphertext and its separately signed `<archive UUID>-origin.json`. The packet binds the actual original enrollment anchor, protected issuer/current generation, source file identity, exact schema41 manifest, ciphertext/snapshot hashes, immutable SQL binding and historical TLS public keys. The actual guarded online-copy capability preserves its consistent SQLite read point when business writes commit concurrently. Caller JSON cannot assert that capability. Preparing origin for an older archive without that private capability requires the stricter independently verified current-source comparison.
3. Configure a NEW private local NTFS backup directory with absolute path length at most120 UTF-16 characters, and a distinct NEW export directory at most200. These bounds reserve space for the existing job/try/verification names used by Windows inbox helpers. Unsupported protected layouts are rejected before credential input; existing roots are never moved or repaired. Existing TEST-only configurations retain their separate behavior.
4. Export the ciphertext AND authenticated origin packet. The worker verifies signatures/hashes and uses flushed, exclusive, no-overwrite publication. Existing matching final files are checked; mismatches fail. Interrupted pending files are retained and new publication attempts use new private pending names. Jobs retain their original UUID and durable state; FAILED is terminal. Never mark an export physically off-device merely because a local folder drill passed. Retention currently preserves all archives pending owner storage/retention acceptance; there is no destructive pruning or mandatory cloud dependency.
5. Replacement preparation requires B plus independently pinned signer trust, a new empty private UUID destination and explicit trusted TEST replacement/old-device-fence confirmation. B is decryption-only and cannot sign archives, issue sessions or promote a writer. A missing/invalid origin packet remains read only/original-root-bound; never invent a legacy anchor. The consumer does not need the original DPAPI root or its original configuration.
6. The importer verifies complete authenticated ciphertext, independently reopened reviewed41 SQL, integrity/FKs, every typed row and hidden rowid, credentials, immutable original binding and financial/Settings history. It creates fresh destination IDs, TLS private-key identity and role signing secrets. An original or historical TLS public key is forbidden, including a reissued certificate using the same private key. Original credentials and financial/audit rows are preserved; accounts are never reprovisioned.
7. The new DPAPI/ACL receipt is distinctly `POS_IMPORTED_ROOT41_V1`, never a forged ENROLLED receipt. Its separately receipt-bound native ledger format retains the original candidate-journal rules for original roots. INTENT precedes the target SQLite copy; only a positively acknowledged copy can obtain the restricted Admin-verification capability. That capability grants no Staff/session/business/password-reset access. A fresh Admin receipt must pass through the SAME sole owner and callback-scoped handoff before COMMITTED/CURRENT publication under the pinned runtime lease.
8. Unknown SQL/copy completion never becomes authority from schema equality or a matching fingerprint. Retain the target, receipts and every orphan; use deliberate permanent QUARANTINED_NO_ADMISSION, or leave unavailable if provenance itself is partial. Native publication locks and terminal records fence delayed helpers. Do not replay SQL, re-copy an uncertain candidate, overwrite files or claim rollback. Start a separate approved attempt only in a new identity/directory.
9. A durable COMMITTED record can be deliberately finalized after independent validation, fresh existing Admin verification and renewed trusted TEST fencing confirmation. Never reconstruct COMMITTED from SQL alone. If CURRENT was published but its reply was lost, read the protected journal and reconstruct admission; do not publish a second completion or repeat SQL. Every startup validates the latest generation, actual vault/file IDs, historical provenance and live runtime ownership. Source sessions are invalid and both roles log in again.
10. Subsequent protected41 restore uses the same quiesce/drain/sole-owner handoff, separate target, fresh keys and protected restore provenance. Immutable historical Settings prefixes remain validated while new commands use the new file namespace. Latest CURRENT durably retires earlier sources for current-code admission. Worker configurations cannot silently follow a different database namespace. A local journal cannot remotely revoke an offline clone or prove a former machine was physically fenced.

Actual-owner/hardware acceptance remains BLOCKED or NOT VERIFIED: two separately protected owner-held B copies and separately controlled signer trust/custody; retrieval on a real replacement Windows account/PC without the original DPAPI profile; witnessed former-device fencing; trusted production TLS; approved storage/media/retention limits and RPO/RTO; target hardware power-loss, disk-full and capacity tests. No physical second-PC, custody or power-loss PASS is implied by process-kill/local-folder tests. Unknown/lost Admin credentials remain blocked by the unapproved R/reset policy. Production enrollment, real custody activation, deployment and production promotion are not authorized.
