# Phase2 desktop original-key durability: bounded security decision

15 November2026. OWNER APPROVED items1–4 on 15 November2026. Implementation and acceptance pending. Disposable TEST only; production disabled.

## Concrete finding

Approved desktop item4 requires fresh in-memory role partitions and clearing browser state. desktop/main.cjs implements that exactly, including clearStorageData on role-window close. Seven existing web recovery stores (sales, inventory, returns, expenses, invoices, cash, settings) retain their original operation keys/context/state in IndexedDB. The existing Backup/Restore card also retains original job/optional archive UUIDs in localStorage and has the same loss problem. Electron's documented clearStorageData clears IndexedDB, and in-memory sessions have no persistent storage path. Consequently the current desktop model cannot preserve those client recovery markers across role-window close/process death. SQLite idempotency still protects an ORIGINAL known key; a newly generated key after losing that marker cannot provide equivalent uncertain-operation recovery. Backend-only crash tests retain keys in the test parent and do not prove renderer-key durability.

References: [approved desktop model](PHASE2_DESKTOP_ARCHITECTURE_REVIEW.md), [Electron session API](https://www.electronjs.org/docs/latest/api/session#sesclearstoragedataoptions).

## Proposed grouped TEST scope

1. Retain RAM-only browser/auth sessions. Persist ONLY the existing strictly typed recovery-marker metadata (module, role, UUID key, context digest, kind, state and format; optional strict archive UUID for existing Admin backup markers), in a separate protected CurrentUser-DPAPI native checkpoint under existing retained private TEST data. No passwords, cookies, bearer tokens, financial payloads, quantities, prices or customer details.
2. Add a narrowly sender/main-frame/origin validated preload bridge for these fixed marker operations, with no renderer-selected file paths, SQL, shell, namespace or authority. Bind checkpoints to the native validated active database/generation and role; never silently reuse old restore namespaces. Existing gateway authentication/authorization must independently verify each sensitive checkpoint access through a private fixed-purpose callback; cookie presence, URL or renderer flags are never authentication. No second account writer or business transaction API.
3. Durably acknowledge marker writes BEFORE financial HTTP submission, with exact compare-and-swap/one-use state transitions, bounded storage and fail-closed publication/readback. Rehydrate only the existing original-key recovery flow after genuine role login; no automatic financial replay, new keys on uncertain outcomes, cancelled-state deletion or credential bypass. Marker clearing follows existing confirmed/known-safe rules only.
4. Make only the necessary functional storage-adapter integration in the seven existing recovery-store helpers and the existing Backup/Restore marker adapter (eight marker families). Preserve all approved frontend DOM/layout/classes/receipt visuals. Keep browser fallback behavior unchanged. Verify role/guest isolation, forged/stale/retired metadata, native write failures, interruption before/after checkpoint acknowledgement, UNKNOWN COMMIT, actual EXE kill/restart, logout/relogin and preserved originals. Do not accept release artifacts until this gate passes.

Alternative: keep original-key desktop restart recovery explicitly FAIL and block release. Silently persisting complete browser profiles would conflict with approved item4 and also fails to solve changing HTTPS port/origin namespaces by itself.

Approval basis: AGENTS.md says "Ask before destructive operations, deployments, or major architectural changes." Approved desktop architecture reserves material changes. The approved native restore-authentication items1-5 do not authorize this separate business-marker persistence/renderer bridge. This is one new grouped decision, not reapproval of earlier architecture or recovery primitives.
Evidence: actual official Electron45.3.3 session API probe exited0 and reported inMemoryRolePartition=true/storagePath=null (ignored native-session-check-5e3d63af-bdf0-492f-a267-f765d2c50c8c/result.json). No financial operation was executed by that probe. Browser marker loss follows from the verified session configuration, existing marker-store source and documented clearStorageData behavior; this is not a fabricated UNKNOWN-COMMIT test result.
